SERVER WORKFLOW
1. Clone with Git LFS, or extract the standalone archive into its own working
   directory. Keep the alvir/ directory structure. Inspect GPUs with nvidia-smi.
   Respect any existing scheduler or CUDA_VISIBLE_DEVICES allocation.
   Do not install system software or change drivers unless authorized.

2. Use Blender 4.5 LTS, preferably 4.5.9, with NVIDIA CUDA support.
   Official downloads: https://www.blender.org/download/lts/4-5/
   Set a shell variable to the available Blender executable, for example:

   ALVIR_BLENDER=/path/to/blender

3. Benchmark one visible CUDA GPU (five representative 4K frames):

   "$ALVIR_BLENDER" -b -t 8 --python-exit-code 1 \
     alvir/output/alvir_walkthrough.blend \
     --python alvir/scripts/remote_render.py -- \
     --backend CUDA --gpu-index 0 --benchmark --samples 32

   The script prints AVAILABLE_GPUS, selected devices, and frame times.
   Inspect the rendered benchmark images in alvir/video/remote-benchmarks/.
   For a quick diagnostic, add --width 1280; then benchmark native 4K.
   Still-frame timing includes setup. A 12-frame animation range gives a
   better sustained-speed measurement:

   "$ALVIR_BLENDER" -b -t 8 --python-exit-code 1 \
     alvir/output/alvir_walkthrough.blend \
     --python alvir/scripts/remote_render.py -- \
     --backend CUDA --gpu-index 0 --samples 32 --start 1 --end 12

4. Render with the selected GPU indices from AVAILABLE_GPUS. Example for
   one GPU; change --gpus to 0,1 or 0,1,2,3 only if those devices are
   available and allocated to this task:

   python3 alvir/scripts/run_remote_workers.py \
     --blender "$ALVIR_BLENDER" --gpus 0 --samples 32

   The launcher partitions all 2160 frames into disjoint ranges. Workers
   write alvir/video/frames-cycles/ and their own logs. Existing complete
   frames resume automatically. Keep the same Blender version and samples
   across workers. A profile check prevents mixing incompatible caches.
   If samples/settings change after benchmarking, preserve or move that
   benchmark/production cache before starting the new settings.

   Another option is one Blender process using all visible CUDA GPUs:
   omit --gpu-index when calling remote_render.py. Benchmark before
   choosing between multi-device rendering and one process per GPU.

5. Do NOT mix Cycles and EEVEE frames. The remote Cycles profile restores
   the original model's sky lighting and can run without EEVEE's display
   context. EEVEE is an alternative only after its GPU graphics backend
   is verified on the server. Its frames go to frames-eevee/.
   All 2160 frames of the final film must use the selected profile.

6. Encode once every frame is complete. The encoding script needs Python
   Pillow, FFmpeg, ffprobe and Arial or DejaVu Sans. Use an existing Python
   environment or a project virtual environment. Example:

   python3 -m venv .venv
   .venv/bin/python -m pip install Pillow
   .venv/bin/python alvir/scripts/encode_walkthrough.py \
     --frames alvir/video/frames-cycles \
     --output alvir/video/alvir_walkthrough_90s_4k.mp4

   Encoding adds titles, model uncertainty text, music and source credits,
   fades and chapters. It checks all source-frame dimensions, the 90 s
   audio/video streams and frame count, then decodes the entire MP4.
   Final verification report: alvir/video/video-check.json.

7. Inspect frames from all five shots, the transitions, and the last
   credit screen. Check audio and visual playback before delivering.
   Deliver the finished MP4 with credits.txt. Do not claim completion
   merely because render jobs were launched. Publish the finished MP4
   through Git LFS with its validation report and credits in this repository.
